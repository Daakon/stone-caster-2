# Play screen redesign: implementation plan for approval

Status: **planning only**. No phase is authorized by this document. Read with [SPEC.md](SPEC.md), [ROADMAP.md](ROADMAP.md), [tokens.css](tokens.css), and every board in `boards/` (including `as-built/`).

## Executive summary

This is a two-milestone content/data foundation plus eight play releases. The **pre-setup milestone** covers the guarded wipe, ownership and stable-key sources, least-privileged standalone sync, frozen compile snapshots and session pinning. Phase 0's tokens and shell can proceed in parallel; its game setup and state loader wait only for pre-setup. The **pre-launch milestone** adds cross-instance content invalidation, release publishing, real deletes, snapshot garbage collection and tier controls before real players are admitted. Phases 1–7 retain the turn, narration, knowledge, mobile, conversation, HUD and combat work. The largest risks are a destructive cutover, an internal-content authorization leak, stale content on a Fly instance, a compile/garbage-collection race, and the existing turn/balance race. No pre-wipe game save is carried forward.

Transport is **resolved** by SPEC §2.1: the existing `POST /api/games/:gameId/turn` streams ordered JSON events over HTTP; an authenticated GET status endpoint recovers a dropped stream. Stonecaster's foreseeable single-player turn flow has no server-initiated updates requiring a persistent WebSocket.

The settled turn, funding and knowledge decisions remain. First-party source content lives as **current files in the repo**, with Git as its history; a standalone validated command deploys it without rebuilding either app. Authoring references use stable keys. Compiled stories freeze resolved content by hash, and sessions pin their compiled story. First-party content has `internal|published` release state; admins alone can test internal content. Players may create and delete their own stories, worlds and entities, but **cannot create rulesets at launch**. Tiers limit owned stories and saved games; story export/import lands in Phase 5. No numeric turn price or tier limit is set by this plan. Approval of the plan and the controlled wipe window remains required before foundation execution, while Phase 0 layout work may be developed independently after plan approval.

### Revision note: transport decision (2026-09-26)

SPEC §2.1, §9 and §10 settle the transport. The previous draft proposed a WebSocket server, subscription-token route, dependency, and reconnect test. Phase 1 uses a fetch-readable NDJSON response from the current turn POST plus durable, per-request progress and a GET status check. Phase 2 sends provisional narration on the same response and replaces it with canonical validated blocks only at commit. There is no socket, subscription route, or push channel in this plan. A dropped response does not cancel the turn; any authenticated device can find the active request by game, read its durable provisional view, then load the committed result or safely retry after a verified failure. This change is limited to turn delivery, recovery, related files, and tests; the remaining phases and contracts retain their scope.

### Revision note: game-level turn claim and reserved balance (2026-09-26)

The earlier Phase 1 only deduplicated one `client_request_id`; it could let two different IDs for one game reach AI calls and had no active balance hold. Phase 1 now locks the game state, checks **any** live running claim first, checks exact-ID replay next, then checks a shared per-user-per-game rate window and spendable balance before atomically claiming and reserving cost. Worker-owned lease renewal, fencing, settlement, failure release, and stale-claim reconciliation keep one active turn and one hold across instances. A duplicate returns the running request's status URL and uses the same progress card, with no client cancel. The active Chimera code has no wallet or charge ledger, so this revision adds the required backend schema and tests instead of assuming legacy wallet code works.

### Revision note: cross-device progress and durable step previews (2026-09-26)

The previous draft used browser `sessionStorage` to remember the request ID and stored only phase labels server-side; Phase 2 explicitly discarded provisional text on stream loss. Phase 1 now adds a game-keyed active-claim GET on play-route load and a lease-epoch-tagged, backend-owned cache for completed Director/Engine outputs. Phase 2 adds durable narration-so-far and player-safe intent/mechanical previews. Each preview is saved in the worker's existing lease-renewal/phase transaction **before** its stream event is emitted, then returned by the status GET from any authenticated device. A committed result replaces the cache; failure or stale-lease reconciliation clears it and retracts it from the client. The final `turn+snapshot+presentation+mentions+charge` commit, balance hold, and one-active-turn claim remain unchanged.

### Review addendum: active-lookup authorization and epoch changes

The game-keyed active lookup is a new data surface, so it must authenticate and verify ownership of `chimera_game_states` **before** reading progress or returning `204`; a foreign/unknown game returns the same non-disclosing 404. The existing `{request_id, lease_epoch, last_seq}` fields already distinguish retries. On a higher epoch for the same request, the client clears its old provisional view and sequence baseline before accepting the new attempt; it rejects delayed lower-epoch events. No schema change or change to final commit/billing is needed.

### Evidence and scope boundary

The active route is `frontend/src/pages/play/GamePage.tsx` → `frontend/src/components/game/ActiveGameInterface.tsx`. It GETs `/api/chimera/play/:gameStateId`, then POSTs `/api/games/:gameId/turn`. The latter runs `GameTurnService` (Director, deterministic Engine, MAS2 Narrator), stores `chimera_turns` and a `dialogue_history` array, and returns a delta and new logs. MAS2 currently calls `LlmService.generateJSON(..., Mas2ResponseDtoSchema)` and returns one `ripple_narrative` Markdown string. There is no HTTP turn stream, model streaming interface, persisted typed blocks, knowledge log, alias table, or HUD manifest in the inspected source. Timing marks exist in `TurnTimelineTracker` but return only with the completed response. Current compiler `config_ui` holds `creation_manifest` and rule labels, not a play HUD manifest. The active genesis path can also omit compiled ruleset defaults, as detailed in Phase 0.

For billing, checked-in migrations have an admin-editable `pricing_config` and a signup trigger `create_user_profile_on_auth_signup()`, but no active reserved-balance account or spend ledger. `AdminConfigService` can update pricing rows, although it does not currently validate pricing values; `ConfigService` caches them and supplies a code fallback, so its cached/default value must never be the authoritative quote. The old `TurnsService` has its WalletService balance/spend calls commented out; `GameTurnService` does not check cost before Director/Jev/Narrator calls. The checked-in `turn_cost_default` seed is historical data, not the plan's fixed price. The old in-memory `rateLimitSendTurn` uses `req.params.id`, is not mounted on the current `:gameId` route, and is instance-local. Phase 1 supplies the transactional primitives, one idempotent starter grant for every existing account at cutover and new account at signup, first-use repair, and admin-only ledger credits. None of those grants is derived from legacy payment, auth or wallet records.

Database claims below are based on checked-in `supabase/migrations/20260201000001_core_tables.sql` and its RLS/index migrations, **not a live Supabase schema**: no DB MCP tool is available in this session. Before implementing the foundation, inspect the target database's columns, constraints, indexes, policies, grants and content rows. Checked-in schema has unique ruleset/world keys and globally unique entity slugs, current compiled-story rows cascade on source-story deletion, and `is_official`/`visibility` appear in access paths. The foundation changes key uniqueness to owner-scoped current rows, removes source-delete cascades from pinned compiles, and adds explicit ownership/release checks, content-addressed snapshots, standalone sync and guarded cleanup. The foundation's live reconciliation is a release prerequisite, not a claim that hosted rows already match the repo.

## Foundation - guarded reset, current content and frozen compiles

**Milestone boundary:** **F0a / pre-setup** gates Phase 0 game setup: guarded wipe and live-content reconciliation; first-party/player ownership; stable-key references; a dedicated-role standalone content sync with basic validation; content-addressed frozen compiles and required session pins. It also supplies a catalog-generation fence so a compile cannot mix two source batches. Phase 0 frontend tokens, shell, layout and accessibility can be built against fixtures before F0a. **F0b / pre-launch** owns the remaining foundation work: multi-instance shared/public and owner-scoped cache invalidation, full format/deploy workflow, admin internal/published release controls, real source deletes and missing-ref UI, snapshot GC, tier caps/active-item choice, and the admin/editor UI. F0b may run in parallel with Phases 0–5 development, but all F0b gates must pass before any real player is admitted. Until F0b, setup is restricted to admins/testers and mutable content caches are bypassed or revalidated at the compile generation fence; do not claim production cache/release/tier behavior from that interim path. The wipe is an operator-run approved maintenance action, never a startup hook or ordinary migration.

### F0a — pre-setup prerequisite for Phase 0 game creation

**Evidence and compatibility:** The checked-in export has 16 rulesets, one world (`mystika`), five entities (`cael`, `kiera`, `rillford_square`, `whispercross_glade`, `slavers`), four lore fragments, 42 tags and seven premade characters. These are **test content for exercising systems**, not the launch catalog; roughly eight real worlds may arrive later through the same content pipeline. The live ruleset/source inventory is reconciled against these files before the reset, with the chosen canonical current payload recorded. `supabase/scripts/export-hosted-base.mjs` currently regenerates seed SQL from hosted data. Existing `backend/src/utils/cache.ts` and `templates-cache.ts` are per-process/TTL caches, while `backend/fly.toml` permits multiple auto-started machines; neither provides cross-instance content invalidation. `is_official` and `visibility` have live readers in `backend/src/routes/catalog.ts`, world/entity/story/admin routes, publishing/RLS, and frontend catalog/admin services. Retain both during migration: `is_official` is a read-only compatibility projection of `owner_kind=first_party`, and `visibility` continues the player-content publishing workflow. Neither grants access to first-party internal content. Remove the current `visibility='public' OR is_official=true` catalog/RLS bypass; first-party access checks `release_state`, player access checks owner/visibility/review policy. A later removal of either compatibility column needs a separate consumer migration.

**Controlled wipe:** In a maintenance window, inventory live FKs/policies, take and verify a restorable backup/export, reconcile live rulesets against the checked-in test catalog by stable key and canonical hash, and freeze writes. A restricted one-time script takes a backup receipt, tester-account allowlist and operator identity, checks `chimera_launch_guard.real_players_started_at IS NULL` and absence of a prior `chimera_prelaunch_resets` marker, then deletes prelaunch drafts/compiled stories, worlds, entities, characters, sessions, turns, progress, dependent authored data and test-only financial rows in explicit FK order. Preserve ruleset templates until reconciliation, login accounts, required profiles, admin identities/roles and system configuration (including price/starter settings). The script records row counts and refuses rerun or execution after real-player admission. The guard is set irreversibly before real players are admitted. Because accounts remain, Phase 1 retains the shared-key starter-grant cutover. If a separately approved reset also removed accounts, only that existing-account sweep would disappear. The wipe SQL lives under `supabase/ops`, outside automatic migrations; it creates the guard tables if absent before checking them, and the later F0a migration formalizes the same schema idempotently.

**Current source and ownership:** Authoring references are `ContentKeyRef {kind, owner_namespace, key}` only; first-party namespace is `first_party`, player namespace is the creator user ID. No source revision rows or current-head pointers remain. Authorable rows carry `owner_kind`, matching `owner_user_id`, stable `content_key`, `content_format_version`, `content_hash`, and type-specific fields. DB checks, grants/RLS and a trigger reject player spoofing of first-party ownership; ordinary app routes cannot write first-party rows. The restricted sync function is the only first-party body writer. Player ruleset creation stays disabled. F0a installs `release_state internal|published` with new first-party keys defaulting to internal and permits authenticated admins to test internal content. **Frozen compile and safe deletion:** A story compile resolves all key refs at one catalog generation, validates the complete dependency graph and access/release policy, canonicalizes every resolved item (including format version), and hashes its bytes. `chimera_content_blobs(sha256 PK, format_version, body jsonb, byte_count, created_at)` holds each immutable resolved item once; identical content across compiled stories shares a blob. `chimera_compiled_stories.source_manifest` is a compact ordered list of `{kind, owner_namespace, key, sha256}`; `chimera_compiled_content_refs(compiled_story_id, role, kind, owner_namespace, key, sha256)` supplies FKs to blobs. A compiled payload (engine/UI/prompt output and frozen title/metadata) also has a hash/ref, avoiding repeated raw `snapshot_world`/`snapshot_entities` payloads per compile. The compile transaction inserts/locks blobs and refs and publishes a new compiled-story row/current story pointer atomically after a catalog-generation fence; a concurrent source batch causes a retry, not a mixed snapshot. Every game state has a required `compiled_story_id`, and runtime reads only that compiled payload/hash content, never current source. No source edit, unpublish or real delete changes a running game. `chimera_compiled_stories.story_id` and `chimera_game_states.story_id` become nullable or non-cascading origin references, while the frozen title/owner and game `player_id` remain available after a source-story hard delete; current `compiled_story_id -> story ON DELETE CASCADE` must be replaced. Character origin-world references become nullable/snapshotted so deleting a world does not destroy a character or character-scoped notes. Source graph links/draft refs use stable keys and may become unresolved after deletion.

**F0a sync identity:** Create PostgreSQL `LOGIN NOINHERIT` role `stonecaster_content_deployer` with `CONNECT`, `USAGE` only on a dedicated `content_deploy` schema, `EXECUTE` only on its fixed-signature `content_sync_apply(...)` security-definer function, and `SELECT` only on narrow validation/format views. Revoke default/inherited `PUBLIC` function execution and schema/table privileges that would otherwise broaden this identity; give it no other role membership. No table DML, broad schema grant, service-role key, or general write credential is passed to `npm run content:sync` or the content-only GitHub workflow. The function owns graph/hash/format validation and atomic source/deploy-log/generation writes, uses a fixed `search_path`, validates caller and inputs without dynamic SQL, and is owned by a separate NOLOGIN role granted writes only to the content source, generation and deploy-log tables. The production DSN is a protected GitHub **Environment** secret `CONTENT_DEPLOY_DATABASE_URL`, available only to the content deployment job after environment review on the protected branch; staging uses a separate database role/secret. It is never copied into app/Fly secrets, printed in logs, accepted from pull-request code, or stored in repo files. Local sync uses an equivalent environment-scoped credential with the same DB grants. Rotate/revoke credentials through the deploy runbook.

**F0a sync/compile cut:** Repo files contain only current first-party payloads and a format version; Git is their history. `npm run content:validate` and `npm run content:sync -- --target=...` use existing `tsx` tooling and the dedicated deploy role without building either app. The fixed-function transaction validates the proposed graph, canonical hashes and supported format, upserts the reviewed current source set and records one generation/deploy receipt. A compile reads at one generation and rechecks that generation before publishing its manifest; a source batch racing it causes a retry. F0a supports the initial admin/tester content sync and frozen session creation. F0b completes production deploy/rollback, public release, cache propagation and lifecycle gates before launch.

### F0b — required before admitting real players

**Release and real deletion:** First-party content starts `internal`; sync preserves existing release state. Only an authenticated admin may publish/unpublish through a server action that appends `chimera_content_release_events(id, kind, namespace, key, old_state, new_state, actor_admin_user_id, reason, created_at)`. Publishing validates every dependency and refuses an internal/missing one; unpublishing first requires published dependents to be unpublished. Admins may list/select/compile/play internal test content. Players cannot list, select, compile, or start a new game from it, even by guessed key or prior compiled ID; existing pinned sessions continue. Player story/world/entity edits and real deletes are owner-scoped. A draft with deleted/unavailable refs shows each `missing_content`/`unavailable_content` item and cannot compile. A first-party delete is a sync that refuses remaining first-party references. Deleting a source never deletes a pinned game; Phase 4's separately confirmed saved-game delete remains distinct.

**Garbage collection:** A bounded background/manual reaper first deletes compiled stories with **no** game-state FK and **no** story `current_compiled_id` pointer, then deletes blob rows with **no** remaining compiled-content ref. It never deletes a pinned compile, ledger charge, or character note. Source hard deletion does not leave a hidden source tombstone; an unreferenced blob/compile is eventually reclaimed. Compiler, game creation and GC use row locks (`FOR UPDATE SKIP LOCKED` for candidates), FK `RESTRICT` as a final guard, and recheck predicates in the delete transaction. Blob insertion and ref creation share one transaction and lock the blob row; GC locks that same row. A compile racing a delete either retains/recreates the exact hash safely or retries. Game creation locks the selected compiled row before inserting its FK, so GC cannot remove it mid-creation. Story-current pointer updates and compiled GC serialize on the story row. Test each race and make cleanup idempotent with bounded batches/metrics. Do not implement the possible future admin repair of an existing compiled story: reserve an audited, admin-only operation that could repoint a compiled payload after explicit review, with no current route or schema mutation path exposed.

**F0b cross-instance cache contract:** Shared/public mappings use `source:{kind}:{namespace}:{key}`, `list:{audience}:{kind}:{filter}:{page}` and `preview:{kind}:{namespace}:{key}`; owner-private mappings and lists include the authenticated `owner_user_id` in the cache key and are never served across owners. `blob:{sha256}` holds immutable bytes and needs no invalidation. **Scale model and measurement:** At an illustrative 1 million owners making two private edits/day, the owner stream has about 2 million writes/day (23/s average; design-test a 10x peak), but the global stream receives **zero** of those edits. If owners are evenly active on one instance, the new design delivers about 20,000 owner events/day (0.23/s average) to each instance; two simultaneously active devices on separate instances roughly double only those owners' deliveries. If 1% of the same edits affect public/shared views, that is about 20,000 shared events/day (0.23/s average), or 2 million shared-event deliveries/day across 100 instances. Content bodies stay cached; only generation/watermark probes and invalidation metadata hit the DB, not fresh item reads on every request.

## Source-of-truth and conditional rendering contract

Every play element has an `availability` of `available`, `empty`, `locked`, or `unsupported`. Only `available` renders its full module. `empty` renders a meaningful minimal entry (for example “No one else is here” in Here); `locked` renders a redacted slot only when an authored hint exists; `unsupported` removes the element and its macro/menu action. A newly created session that lacks a required declared state field fails initialization before its first save/provider call; the UI does not disguise a loader defect as `empty` or `unsupported`. No component derives an absent stat from `100`, a hidden name from a full entity object, or an inventory from a promise in the UI.

| Element | Authority | Missing/unsupported behavior |
|---|---|---|
| Story title, save, turn | Session-pinned compiled-story title snapshot and successful snapshot/turn commit | Hide save badge until known; use the pinned safe title, never a later mutable draft title or UUID suffix. |
| Location, time, mood, exits, weather | Session scene registry/narrative context and declared world fields | Omit individual chips; Here scene card can show the available place label alone. |
| Present cast | Server presence projection, safe alias + knowledge summary | “No one else is here”; unidentified cast stays under observed alias. |
| Vitals, pillars, resources, actions | Phase 0 verified compiled starting state, then Phase 6 validated HUD manifest paths | Skip unsupported modules; fail new-session creation if a required declared field cannot initialize. |
| Bonds/disposition | Engine-owned relationship values plus knowledge visibility policy | Hide score until revealed; show only permitted qualitative band if known. |

### Migration, fresh-session and client-compatibility handling

The guarded foundation reset precedes source migration and Phase 0 session migrations. It deliberately removes old stories, game snapshots, turns, progress, player characters and dependent authored data after a verified backup; there is no game-save backfill, legacy presentation reader, alias backfill or stat-repair path. New sessions require compiled-story, character and initialization-version pins from their first insert. Current sources may change or be deleted, while immutable compiled blobs remain until no session or story pointer refers to them; a recompile affects only subsequent sessions. The Phase 1 funding cutover still iterates retained `auth.users`, uses the configured amount and shared `starter:v1` idempotency key, and never reads legacy transactions. Login, play load, game initiation and claim repair missing accounts/grants. Admin credits are separate immutable, reasoned, actor-attributed ledger entries; no balance is inferred from `payment_sessions`, `auth_ledger` or old WalletService code.

Keep the final `turn+snapshot+presentation+mentions+knowledge+progress-finalization+charge` commit atomic and unique by `(game_state_id, client_request_id)`; progress checkpoints are separate non-authoritative lease/phase/cache writes. Enforce a unique `(game_state_id, turn_index)` for new turns. Claim/hold functions are the only write path for game turns; replace any alternate route that calls `GameTurnService` without a claim. Keep progress and charge references for reconnect/status and audit, with documented retention after canonical turn and ledger replay; clear step cache on commit/failure. A dropped HTTP response does not erase the outcome or hold. Initialize aliases for new sessions from hash-pinned authored names and observed `visual_name`/`is_known`, suppressing hidden true names. New turn rows store only player-safe Narrator output; `thought_chain` belongs in restricted audit storage, and direct client grants on raw turns/game state must be tightened before exposure. Test direct Supabase access and HTTP projections. RLS/grants are reviewed per migration.

The plain-JSON response on the turn POST remains during older **client** rollout, behind the same claim/charge/safe-projection path as NDJSON. It does not require any old turn row or old save compatibility. Safe unlinked text remains a fallback for a new block that cannot be linked or validated. No persistent WebSocket is introduced.

## Release gates

The **F0a pre-setup gate** alone precedes Phase 0 backend game setup: approve the destructive window, verify a restorable backup, reconcile live rulesets/sources against checked-in test content and canonical hashes, pass the tester-only/real-player guard, execute the one-time FK-aware wipe, and verify retained accounts/admin identities/config/rulesets. The wipe refuses rerun/post-launch execution and never runs at startup or as a normal migration. Prove first-party ownership/RLS and internal admin-only test access, stable-key graph resolution, dedicated deploy-role privilege denial against accounts/ledger/games/config, standalone sync with no app build, coherent hash manifests, and required compiled-story session pinning. Phase 0 frontend shell may start independently; Phase 0 backend genesis waits for F0a, not F0b.

The **F0b pre-launch gate** must pass before any real player is admitted, regardless of which play phase is in progress: content-only production deploy/rollback and format refusal; multi-instance shared/public and owner-private targeted invalidation with missed-event catch-up; admin release audit and internal-content isolation; dependency-safe hard deletes with missing-ref UI; GC races that preserve pinned blobs/compiles; configured default tier, atomic story/game caps, recent-activity defaults and owner-selected active sets; downgrade read-only and delete/upgrade restoration. Load-test private-event volume and per-instance scans at the stated million-owner assumptions. Complete admin/editor controls, DB/HTTP auth tests, Playwright flows and launch-marker checks. F0b does not block admin/tester Phase 0 setup, but no interim F0a-only route may be exposed to real players. The checked-in test world/entities are not a launch catalog.

Each play phase completes only after its ROADMAP acceptance line is met, changed workspaces pass lint/type-check, relevant unit/component tests pass, and focused Playwright flows pass against **new hash-pinned sessions**. Phase 0 proves compiled ruleset defaults reach player/NPC/world/system state before first save/provider call, requires non-null compiled-story/character/initialization pins, and shows real interim HUD values. A story recompile cannot change an existing session's pinned compile; F0b separately proves source deletion cannot change it. There is no legacy repair gate.

Phase 1 proves streamed HTTP phases flush through the deployed proxy; a second authenticated device discovers a live claim and durable safe step outputs without shared storage; the active lookup denies non-owners before even a `204`; higher lease epochs reset client sequence comparison; concurrent IDs on one game reach at most one provider flow; no provider runs before reservation commit; and committed/failed/stale attempts reconcile holds and ledger exactly once. A live admin price edit changes only later reservations. Signup survives missing grant config/trigger failure; the shared starter key funds every retained existing account at cutover and new account at signup; login/play/claim repair misses without double-credit; and reasoned admin credits use immutable ledger entries under account locks. Billing rollout requires a reconciled existing-account cutover report and configured operational price/grant values, while signup remains available if funding is temporarily misconfigured. Phase 2 proves every emitted preview was durable before delivery, status GET reproduces current-epoch narration/mechanics after stream loss, and commit/failure replaces/retracts it without making preview game truth or a charge; Phase 0/1 sessions receive idempotent aliases from their pinned compile before linked rendering. The plain-JSON older-client transport remains tested during its rollout window; no old-save adapter is required.

Phase 3 proves visible correction History and character-scoped notes with a required, ownership-verified character pin. Phase 4 proves real saved-game deletion preserves ledger and character notes, refuses a live claim, and leaves unrelated games intact. Phase 4/5 show the same notes in Character/Codex across stories. Phase 5 proves `StoryBundleV1` export/import ownership, graph validation, first-party key-only dependencies, new IDs, tier-cap atomicity and refusal of rulesets/saved games. Phase 6 passes its manifest/compiler/projection matrix for **every** supported first-party ruleset in the refreshed current inventory and pinned hashes still used by live sessions. HUD or instruction fixes sync changed current hashes; a new compile adopts them while an existing compiled story/session remains pinned. Use mock AI for deterministic acceptance, then one real-provider smoke for Phase 2 text contract without treating provider quota as a code pass. Preserve authorization boundaries, keyboard access and a single source of truth at every cutover. Stop before foundation implementation until this revised plan is approved.
